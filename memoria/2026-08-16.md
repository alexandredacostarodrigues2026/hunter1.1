# Parte 3 — Simulação NCM2 vira aba (a primeira)

## Resumo Executivo

Pedido do usuário: "crie tb aba para tabela ncm que deverá ser a
primeira". A tabela de Simulação NCM2 (seção separada, acima do
container de Filtros, desde 2026-08-15) e as 3 grades (Entradas/
Saídas/Estoque, já em abas desde a Parte 1 de hoje) se uniram numa
ÚNICA barra de 4 abas, com NCM2 na primeira posição.

## Funcionalidades Implementadas

- **`interface._render_simulacao_ncm2_733()`** (nova, extraída de
  `render_consolidado_origens_733()`): todo o conteúdo da Simulação
  NCM2 (gate Gerar/Regerar, tabela com seleção, legenda/botão Limpar
  filtro) agora é uma função própria, chamada de DENTRO da 1ª aba.
  Devolve o `ncm2_selecionado` (possivelmente atualizado por um clique
  nesta mesma execução) pro chamador.
- **`interface._render_grades_produtos_733()`**: passou a RECEBER
  `abas_por_origem` (dict já criado pelo chamador) em vez de criar seu
  próprio `st.tabs(...)` — as 3 abas de origem agora são 3 das 4 abas
  da MESMA barra, não uma barra separada. Também recebe `ncm2_
  selecionado` (só pra legenda "Restrito ao Capítulo NCM X").
- **`render_consolidado_origens_733()` reordenada**: Consolidado gate →
  Filtros (Busca/Ano) → as 4 abas são CRIADAS (`st.tabs([NCM2,
  Entradas, Saídas, Estoque])`) → conteúdo da aba NCM2 RENDERIZA
  PRIMEIRO no código (mesmo sendo a aba visualmente à esquerda — ordem
  de execução ≠ ordem visual) → só então `filtrado_base` é montado (já
  com o `ncm2_selecionado` atualizado) → conteúdo das 3 abas de origem
  renderiza por último. Esse cuidado evita que o filtro por Capítulo
  NCM fique "um clique atrasado".
- **Removido o `return` antecipado** quando o Consolidado ainda não foi
  gerado: a aba de Simulação NCM2 não depende dele (fonte própria),
  então precisa continuar acessível mesmo sem o Consolidado — as 3
  abas de origem simplesmente mostram "Nenhum item." nesse caso.

## Testes Realizados

- **`streamlit.testing.v1.AppTest`**: 4 abas confirmadas, 1ª contendo
  "NCM2" no rótulo; selecionar a 1ª linha da tabela NCM2 (Capítulo

  4.277→182, Saídas 4.682→529, Estoque 5.976→976 linhas) — confirma

# Parte 5 — Corrige campos de edição vazios (bug real, print do usuário) + remove frase redundante

## Resumo Executivo

Usuário mandou print da tela real mostrando os 3 campos editáveis
(Nome/Código/Unidade) VAZIOS mesmo com o banner de confirmação
mostrando o produto certo (BOLACHA MANTEGA DO SERTAO JUCURUTU, Cód.
013990, Und) — bug real que o `AppTest` não tinha pego antes (a
verificação anterior só conferia `session_state[key]` programaticamente,
que sempre voltava certo). Também pediu pra retirar a frase "Nenhum
produto selecionado como Alvo..." que aparecia mesmo na aba NCM2 (a
seção de alvo ativo não é escopada dentro de nenhuma aba — fica abaixo
de toda a barra, visível não importa qual aba esteja selecionada).

## Causa Raiz (suspeita, campos vazios)

Os 3 `st.text_input` usavam uma `key` FIXA por campo, pré-semeada via
`st.session_state[key] = valor` ANTES do widget ser instanciado nesta
execução (mesmo padrão "seguro" já usado pra `_733_limpar_grades`).
Isso bate certinho no `AppTest` (que resolve `st.rerun()` internamente
até estabilizar), mas no NAVEGADOR REAL o componente do widget no
frontend pode reter estado de uma instanciação ANTERIOR com a MESMA
`key` sem repovoar visualmente com o valor recém pré-semeado — uma
sutileza de sincronização frontend/backend do Streamlit em torno de
`key` fixa + pré-semeação via `session_state`, diferente de passar
`value=` direto no construtor do widget.

## Correção

- **`key` DINÂMICA por geração** (`st.session_state["_733_edicao_
  geracao"]`, contador incrementado só quando a IDENTIDADE do alvo
  ativo muda — origem+descrição+código originais): cada troca de
  produto vira uma key NUNCA vista antes pro Streamlit
  (`edicao_descr_alvo_733_{geracao}`, idem pra código/unidade),
  combinada com `value=alvo_ativo.get(...)` explícito no próprio
  `st.text_input(...)`. Elimina qualquer ambiguidade de estado
  residual do frontend — o widget é sempre uma instância genuinamente
  NOVA quando o alvo muda. Reselecionar o MESMO alvo mantém a mesma
  `geracao` (mesma key), preservando edição em andamento, igual antes.
- **Frase "Nenhum produto selecionado..." removida**: a seção inteira
  de alvo ativo (banner + campos + botões) só renderiza quando HÁ um
  `alvo_733_ativo` (`if alvo_ativo:`); sem alvo selecionado, a seção
  simplesmente não aparece (nada no lugar da frase).

## Testes Realizados

- **`streamlit.testing.v1.AppTest`**: confirmado que a frase antiga não
  aparece mais em nenhum `st.info`. Simulados 2 cliques em sequência —
  1ª seleção (Entradas, "BOLACHA MANTEIGA DO SERTAO 20X250G"): os 3
  campos vieram com os valores CERTOS já na 1ª leitura via `at.
  text_input` (não só via `session_state`, desta vez lendo o VALOR
  RENDERIZADO do widget — `{'Nome do Produto Alvo': 'BOLACHA MANTEIGA
  DO SERTAO 20X250G', 'Código do Produto': '00000000013990', 'Unidade
  do Produto': 'CX'}`); 2ª seleção (trocou pra Saídas, "IOG ISIS
  MORANGO 1L"): os 3 campos ATUALIZARAM corretamente pro novo produto
  (`{'Nome do Produto Alvo': 'IOG ISIS MORANGO 1L', 'Código do
  Produto': '7898034920103', 'Unidade do Produto': 'Lt'}`) — 0
  exceções nas 2 interações. Nenhum dado gravado neste teste (não
  cliquei em "Cravar"), sem artefato pra limpar desta vez.

## Arquivos Modificados

- `OPERACOES/{geraldo_2020_2024,PB_2023_2025,cometa_2021_2025,_MODELO_OPERACAO}/ESSENCIAL/app/interface.py`

## Pendências

- Verificação visual real (Playwright) segue pendente — mesmo com o

  state), ainda não é confirmação num navegador de verdade. Se o

# Parte 6 — Código de maior ocorrência pré-preenchido (produto com códigos ambíguos)

## Resumo Executivo

Usuário mandou print mostrando "REQUEIJAO ISIS LIGHT 200 G" com 2
códigos concatenados na grade ("00000000014928, 0000000100154") e
pediu: "nas entradas, saidas, estoque, em caso de mais de uma um cod
prod, cravar o cód de maior ocorrência". Antes, o campo editável
"Código do Produto" vinha pré-preenchido com a lista INTEIRA
concatenada (texto sujo, não um código só). Agora pré-preenche com o
código que aparece MAIS VEZES nos itens físicos reais do produto.

## Funcionalidades Implementadas

- **`_QUERY_CONSOLIDADO_733_XML`/`_QUERY_CONSOLIDADO_733_ESTOQUE`**:
  nova coluna `COD_ITEM_OCORRENCIAS` — `STRING_AGG(COD_ITEM, ', ')` SEM
  `DISTINCT` (ao contrário da `COD_ITEM` existente), preservando UM
  código por item físico real (repetições incluídas) — necessário pra
  calcular frequência depois, já que `DISTINCT` destrói essa
  informação. Campo interno, não aparece na grade (coluna visível
  continua sendo `COD_ITEM`, a lista distinta).
- **`loader._codigo_mais_frequente_733()`** (nova): extrai o código de
  maior ocorrência de uma string `COD_ITEM_OCORRENCIAS`, via
  `collections.Counter` — empate resolvido pela ORDEM de aparição.
- **`loader.unificar_por_produto_733()`**: reagrega `COD_ITEM_
  OCORRENCIAS` por simples concatenação de string entre os anos
  (preserva a contagem de cada código através da unificação), e calcula
  `COD_ITEM_FREQUENTE` a partir do resultado.
- **`interface._render_grades_produtos_733()`**: campo "Código do
  Produto" passa a pré-preencher com `COD_ITEM_FREQUENTE` (fallback pro
  `COD_ITEM` bruto só se `COD_ITEM_FREQUENTE` vier vazio — cache antiga
  não regenerada ainda). Banner de confirmação continua mostrando o
  `COD_ITEM` completo (lista distinta) como "Cód. original" — contexto
  informativo, não muda.

## Testes Realizados

- **Dados reais da geraldo_2020_2024**: `estagio733_consolidado`
  regerado com a nova coluna (39.686 linhas, `COD_ITEM_OCORRENCIAS`
  preenchida em 39.677). Conferido "REQUEIJAO ISIS LIGHT 200 G" linha a
  linha por ano — código "00000001001546" domina esmagadoramente
  (aparece em quase todo item físico de 2020 a 2025), com "00000000014928"
  e "07898034920127" aparecendo raramente. Após `unificar_por_produto_
  733()`, `COD_ITEM` mostrou os 3 códigos distintos mas `COD_ITEM_
  FREQUENTE` resolveu corretamente pra "00000001001546".
- **`streamlit.testing.v1.AppTest`**: localizada a linha exata de
  "REQUEIJAO ISIS LIGHT 200 G" na grade de Entradas (já ordenada por
  Valor Total), selecionada via `session_state`, campo "Código do
  Produto" veio pré-preenchido com "00000001001546" (não a lista
  concatenada) — 0 exceções.
- Cache `estagio733_consolidado` regerado também em PB_2023_2025 (639
  linhas) e cometa_2021_2025 (3.851 linhas) pra aplicar o schema novo
  nas 3 operações reais.
